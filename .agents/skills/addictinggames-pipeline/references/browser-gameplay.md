# Browser gameplay and recovery

Read when assigning or performing browser gameplay checks. The [main skill](../SKILL.md) owns acceptance, worker scheduling, adjudication and campaign completion. These procedures add browser-specific observations and recovery; they do not launch a run independently.

Before assignments, the supervisor verifies browser navigation, nonempty screenshots, input delivery and a working mute method that preserves the owner's audio preference. Use supported tab/site/browser muting when available; no game must expose a mute button before launch. A setup problem is a lane failure, not a candidate failure. Never change global audio or interact with the owner's session to work around it without authorization.

At most **five pipeline-controlled tabs total**, across browsers, workers and parent, including popups. Record exact browser/tab/worker ownership, reconcile inventory before opening tabs, reuse one tab per tester and let the parent use a freed slot. Avoid accidental popups by navigating to observed destinations. Close only owned extras; blank or close idle game tabs. Preserve owner tabs and browser security/sandbox settings.

On control failure: checkpoint the attempt as `tool_failure`; return its unfinished candidate to the queue; rebind once, then have the supervisor inventory owned tabs. Replace a tab confirmed absent/closed, or reassign to a functioning existing slot/alternate supported browser within the cap. A missing tab need not be closed again. If inventory is unavailable, do not guess capacity or create unlimited replacements. After two supervisor recovery passes without a usable lane, record an infrastructure interruption with the concrete fault and next action; continue independent work. Resume testing when the lane is restored. Never bulk-deny untouched candidates or spin indefinitely. Interrupt finished child agents.

Check the browser provider in each worker turn. In this recovery, newly spawned workers had the in-app browser while follow-up turns on the same workers lost it. If that specific failure recurs, close/reconcile the old owned tab and assign a fresh worker with the same required model and reasoning; do not assume the owner must unlock the desktop. Verify the replacement provider before assigning more candidates. This is a recovery path, not a guarantee that fresh workers always restore browser access.

Open the exact URL in a fresh unauthenticated context. Optional sign-in for saves/social features is acceptable if core guest play works. A local nickname is not account authentication. Do not submit personal information, use SSO or grant camera/microphone permissions; test available keyboard/mouse alternatives. A mandatory identity/permission requirement needs the actual gate recorded and an applicable owner rule; unknown preferences require clarification, not invented rejection policy.

Aim for one meaningful input within 60 seconds for an ordinary game; allow 3–5 minutes when heavy assets visibly progress. Movement, a meaningful choice, puzzle interaction or score/combat change is sufficient. Record exact URL, worker/model, guest path, input, visible response, time and evidence. Menus, ambient animation and HTTP success are not gameplay proof; winning or finishing is not required. Stop after the bounded acceptance observation.

Record direct and iframe outcomes separately. If direct guest play works but the site's restricted iframe fails, use external play. Do not loosen sandbox permissions. An apparent game failure gets an initial test plus two focused retries, including a second worker and another supported lane/control path where available. Only functioning-tool observations count as failed gameplay attempts. Tool failure stays pending even after recovery is exhausted.

An exact owner confirmation can supply gameplay acceptance with its statement reference and access conditions. Never invent agent input or infer that an unspecified set of games was confirmed. Prior inconclusive attempts cannot override later exact confirmation. Recheck when destination changes or the owner requests it; still verify AI authorship separately.

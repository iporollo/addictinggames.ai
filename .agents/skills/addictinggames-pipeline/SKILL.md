# AddictingGames pipeline

Use only for `iporollo/addictinggames.ai`, production `https://addictinggames.ai`. Verify checkout remote, current main and local changes. Read `AGENTS.md` and `game-discovery-bot/owner-decisions.json`. The verified checkout owns these instructions; when maintaining installed/workspace copies, synchronize the entire skill directory (including scripts/references) and the workspace guidance, then compare contents. Do not edit an older checkout through a stale guidance symlink. Current direct owner instructions override older policy; distinguish explicit owner exclusions from historical agent holds. Historical reports describe attempts, not new acceptance requirements. Preserve them.

## Scope and campaign clock

A full-pipeline request authorizes discovery, verification, artwork and publication of successful batches through the existing commit/PR/CI/merge/deployment/live-verification path. A narrower request authorizes only that phase. Editing or discussing these instructions never launches Scout, retests candidates or publishes. An exact supplied list is closed scope: process it without launching Scout unless discovery is requested.

Use the discovery duration the owner supplies; if none is supplied for a new search, ask for it before launch unless the owner explicitly sets an eligible-game target in place of a duration. There is no default candidate cutoff or inferred publication target. Persist duration or explicit target, scope and any explicit batch size before launch. A batch size controls release grouping, not total campaign eligibility. An explicit additional candidate cap must be reconciled with a full-duration request before launch; do not silently shorten the duration.

Record one acknowledged Scout start timestamp; calculate the UTC deadline as start plus requested minutes. Never reset it on resume. Continue research through that deadline, including partial final waves and replacements for duplicates/invalid leads. Stop new discovery at the deadline and record the stop acknowledgement. Targeted evidence recovery for already discovered candidates continues afterward, along with gameplay, mod review, adjudication, artwork and publication. Do not extend new discovery without authorization.

Maintain one active Scout supervisor. Before launch, reconcile Scout conversation, active project chats, local runs and open release PRs. Missing local records do not prove no campaign exists. Resume an unowned unfinished campaign; never take over another active supervisor. Verify an explicit start acknowledgement before reporting discovery running. Reconcile interrupted message delivery before retrying it.

Before yielding during authorized ongoing work, verify a finite Scout routine or thread supervisor heartbeat is active and recorded, using supported scheduling tools. It must stop discovery at the fixed deadline and then drain all authorized work; notify only on meaningful changes or required action. If supervision cannot be established, report the interruption honestly. A shared tool outage leaves the campaign interrupted and resumable, never complete. Stop temporary supervision when complete or explicitly stopped by the owner.

## Acceptance contract

Keep evidence, final decision and publication status separate. `decision.publish` is null while work is pending, then exactly 1 or 0 after the applicable review route. The main Codex agent may approve a candidate on the first pass when every acceptance gate has saved evidence. Every held or failed first-pass candidate goes to Grok 4.7 High for independent second-pass review before any final 1 or 0. No final held state. A missing receipt creates a work request, not an automatic 0.

- **Browser game:** exact identity, credible game-specific AI creation evidence, responsive guest gameplay from GPT-6 Luna Max or an exact owner confirmation, no published duplicate or owner exclusion, and Tesla selection when applicable.
- **Mod:** exact mod/base-game identity, credible mod-specific AI creation evidence, an actual public release, exact distributed artifact and SHA-256, adequate Codex Security artifact review and no unresolved material blocking finding. Read [mod release and artifact review](references/mod-review.md) for review coverage and public warnings.
- Creator/official evidence that AI assisted code, art, audio, writing or another part of the actual game/mod qualifies. A named tool is not mandatory. A creator's "I made this game with AI/Grok" linked to the exact game can qualify even if the wording resembles a share template. Do not require a mechanics description, source code or originality. Hosting, hashtags, appearance, runtime AI opponents and unrelated creator work alone do not qualify. AI-written promotional listing text alone does not establish AI creation of the game/mod itself.
- No subjective quality gate: simple, repetitive, familiar, unfinished-looking games and playable demos can qualify. Franchise/brand references, fan characters, real-person likenesses, commercial-game inspiration and license uncertainty are warnings, not automatic denials for linking to the official destination. Do not infer permission to redistribute upstream files. Explicit owner exclusions and actual security findings remain separate gates.
- No public repository, X post, ordinary X metrics, named model, positive community comment, or successful iframe test is universally required. Never manufacture evidence or weaken gates to increase throughput.

## Discover and retain evidence

Use the existing **AI Game Scout** conversation in the installed Grok Bot. Send the acceptance contract above, duration/deadline, current catalog exclusions, required evidence fields and incremental-delivery instructions. Scout continuously researches AI-created browser games and mods across public X, creator posts and replies, official listings, and linked project sources for the full discovery window. Tell Scout to keep a sent-link/identity index and submit each candidate link once; it should not restart research or send another candidate for that link. If it later finds materially new evidence during this campaign, attach only that evidence or correction to the existing candidate ID. Owner-supplied AI-Games bookmarks are an optional, supplemental lead source: check them when accessible, but never limit discovery to them, wait for bookmark access, or treat a bookmark as AI-creation proof. Scout supplies exact game/mod-specific AI creation evidence for the first pass. It does not play games, publish, contact creators or message other bots. The main Codex agent verifies that Scout's source and quote actually refer to the current candidate; a lead alone is not approval. Distinguish discovered leads from verified or publishable candidates.

Ingest every delivered item immediately into the single ledger described in [campaign-contract.md](references/campaign-contract.md); do not wait for a whole wave. Preserve every supplied public-source or bookmark lead URL and map it to its candidate, including aliases and duplicates. Expand collections into distinct game identities when supported by exact destinations; do not reject a collection merely because its identities need resolving. Stable IDs never change with disposition. Preserve raw source records and superseded attempts separately.

For AI evidence record the exact quote, exact source URL/type, observation UTC and identity linkage. Follow creator posts, replies, official pages and exposed repositories. Missing/ambiguous evidence goes to focused recovery. Static login strings or JavaScript shells cannot establish mandatory sign-in; send them to browser testing. Find creator-linked playable destinations behind articles and listings.

Deduplicate against current main, live catalog, explicit owner decisions and previous receipts before assigning research or testing. Compare exact content identity, redirects and aliases, not just host/title. Normalize host case and default ports; remove only proven tracking parameters. Preserve fragments, queries, paths, `www` differences and trailing slashes when they may select different content; merge only with identity evidence. Record the matched published slug or canonical candidate. If Scout repeats an exact link despite its sent-link index, attach any new source to the existing candidate and reuse its evidence and decision; do not assign another full research or gameplay/security pass. During admission, a material change to the candidate being reviewed can reopen only the affected gate with a recorded reason. A prior unpublished receipt resumes that candidate rather than excluding it; a new release version does not make an existing mod a new catalog entry. Duplicate leads never consume a useful publication target, and repeated links are not candidate denials. Ongoing checks of games or mods already published on the site are a separate task, outside this discovery-and-admission pipeline.

Retain every exposed source repository in a `source_repositories` array, including denied/duplicate leads: exact URL, discovery source, observed UTC, verified commit/tag if available, license/status. Do not infer repositories from hosting names. A missing commit/license is explicit null with a reason, not an automatic game rejection. Save metadata, not upstream source trees/binaries in the public repository.

For each game-linked X post retain its URL/ID, views, likes, reposts, replies, quotes, observation UTC and retrieval source (official or mirror). Unknown values stay null, never zero. Keep snapshots separate. Missing metrics do not block ordinary publication; Tesla selection and Hot Right Now require their own evidenced rankings.

## Assign verification work

Use five `gpt-6-luna` workers at `max` reasoning for gameplay and, for combined campaigns, three `gpt-6-luna` workers at `max` for mod evidence/Codex Security coordination. Check actual agent capacity first and schedule these roles in waves when they cannot all run concurrently. Reduced concurrency preserves the requested model/reasoning and does not require a model substitution. Disclose capacity limits; never leave the queue unassigned while waiting for impossible concurrency. Do not silently substitute models. Give disjoint candidate IDs and report paths. Workers are not alone in the codebase, must preserve others' edits, and cannot edit the catalog. Reserve gameplay capacity for live tests while its queue is nonempty; source-only audits do not count as gameplay tests.

### Keep the review queue moving

- At each Scout delivery, do cheap identity, AI-source, duplicate, owner-decision and release-availability triage first. Dispatch candidates with sufficient starting evidence immediately; send missing facts to a separate focused recovery lane. Do not make every tester wait for a whole Scout wave, an unrelated mod download, artwork, or Grok.
- The supervisor owns a work-conserving queue: assign disjoint candidate batches to every available gameplay and mod-security worker, then refill a worker's lane as soon as its receipt arrives. Give each assignment an ID list, exact gate to check, evidence inputs, output path and bounded retry rule. Record start/completion times and outcome per candidate so a large `pending` count cannot masquerade as active review. No worker may mark a candidate approved merely because it was assigned.
- Keep gameplay and mod-security lanes independent. A mod's public-source check can run alongside gameplay, but final mod approval waits for Codex Security assessment of the exact release bytes and hash. Browser capacity is five pipeline tabs total; one reused tab per game tester. Workers doing source or artifact inspection without a browser do not reserve a tab.
- Start artwork only after a candidate has final `decision.publish: 1`, including confirmed gameplay for a game or adequate exact-artifact security review for a mod. Then generate A/B options if needed, select and optimize the cover, and prepare release evidence while the next review wave continues. Do not generate speculative artwork for unapproved candidates.
- Track `unassigned`, `actively_testing`, `awaiting_security`, `awaiting_second_pass`, `recovering_evidence`, `approved_unpublished`, `releasing`, and `live_verified` as operational views derived from the ledger, without replacing its schema-v2 decisions. Report counts plus the oldest pending age and the actual capacity/bottleneck when the owner asks for status. A tool-blocked candidate gets a named retry owner and next action; it does not hold unrelated work.

Read [browser gameplay and recovery](references/browser-gameplay.md) before assigning or performing game tests. Read [mod release and artifact review](references/mod-review.md) before researching or reviewing mods. Both use the same campaign clock, candidate ledger and two-pass decision routes. Load the relevant reference for a requested subset; neither reference grants broader authorization.

## First-pass decisions and independent second pass

The main Codex agent leads the first pass. It checks Scout's exact AI creation source against the candidate, identity, duplicates, owner decisions, guest gameplay or the exact mod release/security review, and any Tesla selection. If all applicable gates pass, record `decision.route: "first_pass"`, final 1, and the supporting receipts; do not call Grok. A first-pass failure, missing fact, inconclusive observation or tool failure creates a held candidate with `decision.publish: null` and a checkpointed hold reason for Grok 4.7 High. Never convert the first-pass hold into final 0. If Grok independently confirms a real failed acceptance gate with the required evidence, record final 0 and deny the candidate. Continue publishing unrelated first-pass approvals.

Use **Grok 4.7 High through the authenticated Cursor CLI** as the independent second-pass lead for held candidates only. Confirm the exact available model ID before first use; record it and the Cursor route. Use a new read-only ask session for each held candidate or isolated batch, with supported CLI permissions verified locally; no force/write mode, catalog edits or external mutations. Grok owns the second-pass investigation and final recommendation. It delegates by issuing explicit work orders through the main Codex supervisor; Codex launches fresh `gpt-6-luna` Max game testers or Codex Security artifact reviews, then returns their raw receipts to Grok. Do not claim the read-only Cursor session directly spawned Codex workers. Model unavailability interrupts only candidates needing second-pass review, not first-pass approvals. No silent model/API substitution.

Follow [the Grok-led second-pass handoff](references/second-pass-review.md) for the exact packet, work-order loop, fresh-worker isolation and end-of-workflow tool retry.

Give Grok the current acceptance contract, exact identity/URL or artifact hash, a concise factual hold code/reason and primary raw evidence. Do not include the first reviewer's narrative, verdict argument or past agent holds as authority. Preserve all original attempts privately. Grok issues work orders naming candidate ID, disputed fact, responsible role, fresh observation needed and retry boundary. Fresh workers receive the candidate, rules and test question without the first-pass verdict or persuasive narrative; use a fresh guest session for games and the exact current artifact for mods. Grok receives both raw passes after the fresh work and reconciles contradictions by exact identity, version, access conditions, input and observed response. The supervisor carries out Grok's work orders, tracks the ledger and enforces the written gates; it does not substitute its own second-pass verdict. If Grok repeats a resolved request or invents a gate, correct the instruction against this contract and continue with the evidence rather than endlessly retesting or rubber-stamping it.

Grok returns second-pass 1 only when fresh evidence plus the other current receipts pass every applicable gate. It returns 0 only for a permitted failed gate with evidence and required functioning-tool attempts, bound to the current evidence revision. Changed evidence requires another decision. Grok cannot replace Luna observations, owner confirmation or Codex Security coverage. Route a factual conflict to a focused independent retest, not to the owner for routine yes/no; only an undefined owner policy or required owner-only access may need owner input. Before declaring the campaign complete, retry every tool-blocked candidate once more in a functioning lane after the other work drains. If tools still cannot perform the check, record an interruption and automatic/resumable next action; no 0 for tool failures, a deadline, missing assignment, poor aesthetics, repetition or rights warnings alone. Deterministic validation must pass before accepting a decision, releasing a batch or reporting completion.

## Tesla Roadster selection

Maximum **five unique Tesla Roadster games across the entire published catalog**. Inventory existing entries with identity evidence before selection, counting already released campaign entries once. Preserve existing entries; if already over five, report it and admit no new ones without owner direction.

Reserve this group's new releases until discovery closes. Rank unique candidates by their strongest game-linked X post: views descending, sum of likes/reposts/replies/quotes descending, then numeric post ID ascending. Use complete numeric snapshots for every potential competitor from a recorded selection pass; retain source/time and retry missing metrics twice. Verify eligibility from the top of that ranking until the remaining slots have qualified winners. Lower-ranked candidates can then receive `tesla_limit` even if their gameplay is unresolved, since their recorded rank cannot displace a verified winner; do not claim those games failed. Unknown competitor identity/classification/metrics still blocks selection. Unavailable tools leave ranking interrupted; genuinely unavailable metrics after accessible checks produce `tesla_metrics_unavailable`, not a gameplay failure. Ordinary games need no popularity threshold. If existing catalog entries already fill all five slots, `tesla_limit` needs inventory evidence, not wasted gameplay tests. Recheck occupancy before every release; no automatic removal/replacement of older entries.

## Prepare A/B artwork

- Keep suitable creator/custom covers and usable approved art. For missing or placeholder covers, use the built-in GPT image generator to create two distinct, game-grounded A/B compositions. Base subjects and mechanics on verified game evidence; retain exact prompts, both options, and the selection in the run record.
- Reuse an available visual reference library for style only; use the target game's own sources for subject matter. An absent library does not block normal artwork. Do not build or refresh a reference collection during a game batch or create separate thumbnail research workers.
- **For every newly generated cover, show both A/B options inline before release.** Retained covers need no generated alternatives. In a full pipeline, choose the strongest faithful option without waiting for the user; for a standalone artwork request, let the user choose unless they delegate selection.
- Keep generated artwork text-free by default; standalone artwork may include text when the user requests it. Never expose provenance/status labels such as “Concept artwork” in image pixels or customer-facing card text, titles, alt text, or categories. Keep provenance in internal evidence. Inspect current card slots and image use; preserve existing geometry, optimize only the selected cover, and inspect its crop.

### Hot Right Now in a game release

- Preserve the existing five-card shelf and layout. On the first authorized release of each UTC week, refresh the first two slots from published catalog games. After each day's authorized pipeline release, refresh the last three slots from eligible games in that release, at most once per UTC day. If no slot receipt exists yet, use the current first two and last three cards as the respective baselines.
- For each slot, use one game's strongest post from the preceding 30 days and rank by `sqrt(views × (likes + reposts + replies + quotes))`. Refresh the exact post's complete numeric metrics at selection time. Select only already published games or approved games included in the same atomic release; never select pending, denied or duplicate entries. Missing metrics do not qualify for the shelf but do not block ordinary catalog publication. Record post IDs, counts, source, UTC time, ranking, and slot decisions in the run receipt.
- If fewer than three newly eligible games qualify, retain distinct prior daily picks for the open slots. If five evidenced games cannot be maintained, leave the shelf unchanged and report why. Include any shelf change in the same site PR as the authorized game release; discovery-only work never changes it.

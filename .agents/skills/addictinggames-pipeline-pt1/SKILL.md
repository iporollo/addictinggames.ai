# addictinggames-pipeline-pt1

Use this skill for discovery, gameplay checks, artwork, or a full AddictingGames.ai batch. The production site is `https://addictinggames.ai`; the repository is `iporollo/addictinggames.ai`. Verify the checkout's remote and current `main` before acting. Read `AGENTS.md` and `game-discovery-bot/owner-decisions.json`; owner decisions are authoritative. Deduplicate against current `main`, the live catalog, prior run receipts, and owner decisions. Resume an unfinished run from its records instead of starting a duplicate.

A full-pipeline request authorizes one batch from discovery through commit, push, PR, merge, and production verification. User-specified discovery duration and candidate limits override the defaults for that run; persist them before starting and keep one final publication batch. A request for a narrower phase authorizes that phase only; it does not imply publication. Editing or discussing this skill never launches the pipeline.

## Discover AI-created games

- Use the existing **AI Game Scout** conversation in the installed Grok Bot. It discovers from X posts, threads, and creator replies; it does not play games or publish.
- Keep one active run and one supervisor for this Scout. Before a new run, check its conversation, available run records, active project chats, and open release PRs. Missing local records in a fresh checkout do not prove there is no active run. Resume only an unowned unfinished run with its original quota/deadline; do not take over another active supervisor. If ownership or state cannot be established, ask before starting discovery.
- Startup proof: an idle/status reply is not a launch. Deliver the launch brief, verify Scout's explicit start acknowledgement, persist the configured deadline, and enable bounded supervision before reporting the pipeline running. After interrupted UI access, rebind the app and inspect current state before retrying; reconcile delivery to avoid duplicate starts.
- For a timed multi-wave request, keep one campaign deadline and continue waves without another owner prompt. Continue through the deadline even when there is too little time to fill another wave: save a partial final wave instead of stopping early. A batch boundary or estimated search-pass duration never shortens the authorized window. Check the current clock immediately before sending a resume instruction; at or after deadline send stop and receipt-only reconciliation, never resume. Before yielding the chat, verify a finite Scout routine or this chat's supervisor heartbeat is active and recorded; its continuation must ingest, assign gameplay, prepare art, stop discovery at deadline, then finish one release. Notify only on meaningful changes or a blocker; stop temporary supervision when the run is complete.
- Send a filled brief with the configured quota, current catalog/prior-URL exclusions, exact playable and X URLs, and AI-evidence fields. Ask for incremental results and explicit start acknowledgement; do not claim discovery is running without it. On confirmed start, persist start + configured duration (default 60 minutes) as the absolute UTC deadline and communicate it to Scout once; never restart the clock on resume. The brief is discovery-only: no gameplay, publishing, messages to other bots, or unrequested scheduled routine. The parent supervises a stop request and acknowledgement at quota/deadline; gameplay continues after discovery closes.
- Search for games whose creator or official game page explicitly says that **the specific game was created using AI**. For every candidate, record the exact quote, source URL, source type, UTC observation time, and evidence status. A model/tool mention qualifies only when the statement ties it to creating that game. AI hashtags, hosting, appearance, opponents, or unrelated creator work do not qualify. Missing or ambiguous evidence means `held`, not non-AI.
- Stop discovery at **25 new, deduplicated candidates or 60 minutes**, whichever comes first. Count candidates after identity/current-main/live/prior-run deduplication; do not search indefinitely to replace held entries. Send and record a stop request and acknowledgement, or mark the stop unconfirmed.
- The supervisor maintains one ordered candidate queue across all X threads in the run. Preserve whole-thread results; accept only the remaining quota and mark additional new candidates as overflow. Duplicates do not consume quota. With 24 new candidates, a three-new-game thread adds one in-quota game and two overflow games, regardless of busy gameplay workers.
- The minimal candidate record includes ID, title, creator, exact X URLs, exact discovery and playable URLs, retrieval time, dedup result, and `ai_authorship: {quote, source_url, source_type, observed_at_utc, status}`. Keep authorship evidence separate from gameplay evidence.

## Verify gameplay

- Default to **five `gpt-6-luna` gameplay workers at `max` reasoning**, with disjoint IDs, separate report paths, and isolated tabs; keep workers idle when no eligible test is queued. Workers must not edit the production catalog, must not revert other workers' files, and must report when blocked. The parent supervises and establishes a verified mute method before opening games, preserving the owner's current mute preference. If the model or five-worker capacity is unavailable, disclose the limit and ask before changing those settings.
- Hard browser limit: **at most five pipeline-controlled browser tabs open across all workers and the parent, one per gameplay tester**. Reuse that same tab for source verification and sequential games; no separate source tabs, extra windows, or browser sessions. The parent must use a freed tester slot for visual/release checks. Record each worker's sole tab ownership in `run.json`, verify the total before opening a tab, close surplus owned tabs immediately, and close or navigate to `about:blank` when idle so games stop consuming resources. Never close the owner's unrelated tabs.
- The cap includes temporary popups. Before following a game/source link, inspect its observed destination and tab-opening behavior; navigate the sole tab to that exact destination when the link would open another tab. Check owned-tab inventory after navigation and close accidental owned extras before continuing. If browser control is interrupted, rebind the same tab once, then continue independent source review with gameplay held; never open a replacement until the old tab is confirmed closed. Avoid global native browser actions while the owner or another worker is using that browser.
- Open the exact playable URL, sample loading progress, and allow roughly 3–5 minutes for heavy assets when loading continues. Enter gameplay, use relevant controls, and record each input with the observable response. A title screen, animation, HTTP success, or menu alone is not a pass; describe the observed test honestly without claiming a complete playthrough.
- Record direct-play and iframe outcomes separately, using `not_tested` when appropriate; test the site's actual iframe only for embedded inclusion. For pointer lock or focus issues, follow the game's prompt and try an appropriate supported isolated browser when useful; never loosen browser security or iframe permissions. A browser, focus, login, or loading limitation is `held` with a retry reason, not proof the game is broken. Use `agent_verified` only for observed responsive play; use `owner_confirmed` only with a separate owner statement. Read owner decisions before changing any prior hold or exclusion, and preserve historical test evidence.
- Each candidate ends as eligible, held, excluded, duplicate, or overflow. Eligibility requires **both** verified AI authorship and responsive gameplay (`agent_verified` or separately recorded `owner_confirmed`); an owner gameplay confirmation never replaces AI evidence. Never publish held, excluded, duplicate, or overflow entries.
- Close each worker when done: interrupt completed child agents and close only tabs they own. Keep browser security and iframe sandbox settings unchanged.

## Prepare A/B artwork

- Keep suitable creator/custom covers and usable approved art. For missing or placeholder covers, use the built-in GPT image generator to create two distinct, game-grounded A/B compositions. Base subjects and mechanics on verified game evidence; retain exact prompts, both options, and the selection in the run record.
- Reuse an available visual reference library for style only; use the target game's own sources for subject matter. An absent library does not block normal artwork. Do not build or refresh a reference collection during a game batch or create separate thumbnail research workers.
- **For every newly generated cover, show both A/B options inline before release.** Retained covers need no generated alternatives. In a full pipeline, choose the strongest faithful option without waiting for the user; for a standalone artwork request, let the user choose unless they delegate selection.
- Keep generated artwork text-free by default; standalone artwork may include text when the user requests it. Never expose provenance/status labels such as “Concept artwork” in image pixels or customer-facing card text, titles, alt text, or categories. Keep provenance in internal evidence. Inspect current card slots and image use; preserve existing geometry, optimize only the selected cover, and inspect its crop.

## Record and release

- Resolve run paths from the verified repository root. Keep resumable raw evidence under `game-discovery-bot/runs/<UTC>/` and concise, source-linked public evidence under `game-repos/<run-id>/`. Store no credentials, private conversation content, personal absolute paths, or unused generated images in the repository. For deduplication, inspect existing repository receipts and adjacent legacy `../game-discovery-bot/inbox/`, `../game-discovery-bot/runs/`, `../game-discovery-bot/pilot-*/`, and `../thumbnail-research/` records only when present.
- Maintain `run.json` with the run ID/status, supervisor identity, UTC start and fixed deadline, baseline main SHA/live catalog check, Scout start/stop acknowledgements, worker ownership/report paths, ordered candidate IDs, checkpoint/next action, and publication receipts. Checkpoint after ingestion, each test wave, A/B selection, PR, merge, and live verification; reconcile existing PR/merge/deployment receipts before repeating an external action.
- Close discovery before release and give every in-quota candidate a reviewed disposition, with a specific retry condition for held entries. Use `docs/GAME-CATEGORIES.md` to choose each selected game's category; do not change the guide or run a category overhaul. Recheck current `main` and the live catalog. Include exact AI-authorship evidence, exact game/destination URLs, acceptance basis, bounded input/response evidence, and selected-art provenance in the public report. No unrelated catalog, layout, hosting, or security changes.
- A full-pipeline request authorizes one production batch: use the repository's existing catalog and GitHub/Vercel path, run required checks, commit and push one branch, open one PR and attach it to this task, wait for CI, merge under repository protections, then verify the production deployment matches the merged commit. Check every intended New Games entry, destination, selected image response, and live crop. Do not create a substitute Vercel project. If no game is eligible, do not create an empty release.
- Mark a game published only after live verification. Leave a resumable receipt with distinct discovered, reviewed, verified, owner-confirmed, eligible, published, held, excluded, duplicate, and overflow counts; selected A/B choices; source commit, PR, CI, merge and deployment evidence; and remaining limits. State the live New Games URL in the final report.
